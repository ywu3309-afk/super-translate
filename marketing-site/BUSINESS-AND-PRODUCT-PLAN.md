### 有效的页面设计

- 首屏讲“用中文与海外客户沟通”，不先讲模型文件格式或服务器架构。
- 通过聊天示意说明结果，下载 CTA 紧贴产品介绍。
- 浏览器、Windows、Mac、Android、iPhone 使用分开的下载标签，减少选错包。
- 功能 → 界面 → 安装 → 价格 → 场景 → FAQ，顺序基本符合决策过程。
- 分销、通话翻译、AI 客服用独立页面，避免首页承载所有细节。

### 不应照搬的部分

- 不照搬“200+ 语言”“不限翻译字数”等承诺。我们的每条引擎路线、文字与语音模型有不同的支持范围和成本。
- 参考首页有“真实界面示意”“可直接替换图片”这样的维护文案，也存在无实际目的地的 `#` 联系链接。我们的正式页应移除维护说明并验证每个按钮。
- 其 iPhone 安装标签提供 TestFlight，另建议海外 Apple ID / 第三方签名；功能段仍保留自签 IPA 的描述。我们的主要路线应为 TestFlight 内测和 App Store 正式分发，避免依赖不稳定的证书安装体验。
- 页面宣称手机通话实时翻译，不足以证明可在所有系统与原生 WhatsApp 中稳定实现。我们的客户语音消息转写不是实时电话同传。
- 不展示虚构客户评价、用户数量、增长率、官方合作标识或未经验证的平台兼容性。
- 不把基础开源模型说成完全自主训练。可表达“超级翻译 AI 引擎/集成方案”，同时遵守实际模型和运行时许可证。

## 2. 我们的定位

**面向出海销售与客服团队的跨语言沟通工作台。**

区别于单纯翻译器：文字 + 语音理解 + 多账号入口 + 国家识别 + 客户跟进 + 团队授权。不是现阶段就承诺“自动获客、自动成交、所有平台全兼容”。

建议宣传的结果：减少复制粘贴，便于理解外语客户，保留原文方便核对，让客户跟进有记录。可以展示实测的连续五条语音处理，但不把一次测试转化成未经测量的稳定性百分比。

## 3. 收费结构：先简单，再扩展

### 建议的基本结构

收入 = 周期订阅 + 字符加量包 + 语音能力升级 + 团队席位/服务 + 企业实施。

- 同一套餐允许 `1` 个主账号 + 最多 `3` 个子账号。主账号和每个子账号各自仅允许同时在 `1` 台设备上线；电脑、浏览器和手机不因为共用同一账号而获得无限并发设备。
- 文字部分：套餐内字符额度 + 额外字符包。现有预扣、成功确认、失败返还流程需要所有客户端复用。
- 本地 AI 也扣额度、套餐到期也不可用。不能宣传本地版无限免费；也不能宣称客户端本地模型具有绝对不可绕过的授权保护。
- 用户侧尽可能展示统一剩余字符；云端分别记录本地与 API 成本和使用量。若两种字符计费倍率不同，必须在付款前明确，不能暗中折算。
- 当前接口计数采用 JavaScript 字符串长度，其计费单位未必等同于用户理解的可见字符或供应商计量。商业化前应明确 UTF-16、Unicode code point、占位符处理及供应商用量差异。
- 语音识别档位：初级 / 高级多语言 / 旗舰高精度。初期可售卖能力授权并让译文计入文字额度；未来采用分钟额度时，需独立记录有效音频秒数、取整、失败返还和重试去重。**现有系统不能对外宣称已支持语音分钟账本。**
- 实时语音通话如果后续实现，应单独按分钟计价，不包含在“客户语音消息识别”权益里混卖。
- 主账号 + 最多 3 个子账号是目前的组织边界。更多席位、共享知识库、跨设备 CRM 同步是下一阶段，不先收取不存在能力的费用。

### 超级翻译初步定价

以下是已确认的初步商业定价，不是参考站价格：

| 套餐 | 价格 | 文字权益 | 语音权益 |
|---|---:|---|---|
| 200 万字符包 | ¥100 | `2,000,000` 字符，一次性发放，不按月重置，余额用完为止 | 不包含高级语音消息翻译 |
| 450 万字符包 | ¥200 | `4,500,000` 字符，一次性发放，不按月重置，余额用完为止 | 不包含高级语音消息翻译 |
| 高级语音版 | ¥180 | `2,000,000` 字符，一次性发放，不按月重置，余额用完为止 | 客户语音消息翻译不另设时长或次数上限 |
| 月度不限文字版 | ¥300/月 | 服务有效期内不限文字翻译字符 | 包含语音消息翻译 |

所有上述套餐都遵循同一账号与设备规则：`1` 个主账号 + 最多 `3` 个子账号，主账号和每个子账号各自仅可同时在 `1` 台设备上线。

现阶段仅在网页展示上述初步定价，用户注册后由管理员核对并人工开通权益。当前没有自动支付、订单回调或自动发放套餐的已验证闭环，因此页面不得伪造“支付成功”或“立即自动开通”。

“语音”在这一定价中指已支持的客户语音消息转写与翻译，不等同于对 WhatsApp 电话或视频通话做实时同声传译。虽然初步规则不对语音消息另设时长或次数上限，公平使用、异常滥用、服务不可用和退款处理规则仍需在正式销售前明确。

### 为什么不直接跟随 ¥19.9/¥39.9

价格底线需要覆盖：供应商字符/语音费用、服务器与存储、支付/应用商店渠道费用、代理佣金、售后、退款损失。还要分别计算平均客户和高用量客户的毛利。

建议至少继续收集四项：每月活跃用户的 P50/P90 字符量、API/本地比例、语音时长与档位、单客户支持成本。已确认的初步定价可用于展示和人工开通，但在自动销售前仍要根据成本数据确定续费、优惠、公平使用和退款规则，不把一次性字符包误写成每月重置。

特别注意：第三方 DeepL Free Key 的 50 万额度属于供应商账户，**不是每个终端用户各获一个官方 50 万额度**。两个 Key 的可用池也不能解释成可无限复制给客户的配额。商业采购、转售条款、池总预算与客户套餐承诺需要分别确认。

### 分销的阶段顺序

1. 推荐合作：归因链接 + 成交订单 + 退款后净佣金，先验证渠道质量。
2. 代理：独立 reseller 角色，预存余额，开通订单，账本和对账。不能让代理充当全权限管理员。
3. 企业实施：安装培训、客户资料整理、定制配置、支持服务。

“归属”应该是可审计的渠道关系，不是无条件永久占有客户。要定义已注册客户、重复推荐、归因期限、人工变更、退款、注销与隐私请求。不能把普通客户的 3 个子账号功能当成代理系统。

## 4. 多端产品规划

用户已确认：**Android 与 iPhone 做独立 App，不把桌面 EXE 或 Chrome 扩展直接套壳。**

| 端 | 当前状态 | 下一步 |
|---|---|---|
| Windows | `v0.7.38` 已发布；WhatsApp 连续客户语音已实机验证 | 保持正常发送与 CRM 逻辑，持续兼容性回归 |
| Chrome / Edge | 扩展正在上架准备中，未通过商店审核前不标记为已正式上架 | 完成上架材料、隐私披露、权限核对与审核版回归 |
| Android | 已进入实机内测 | 继续实机验收登录、授权关联、WhatsApp 会话、翻译、后台连接和自动更新 |
| iPhone | 规划中 | 独立 App + Share Extension；TestFlight → App Store；键盘单独验证权限、网络与宿主兼容性 |

移动端技术建议采用 Flutter 复用 Android/iOS 的通用界面、账号与请求代码；iOS 分享扩展、键盘、Keychain 等仍需 Swift 原生模块，Android 对应 Kotlin 模块。最终选型前需完成音频导入、权限、模型内存/性能和商店审核要求的小型原型。

手机第一版优先：登录 → 文字翻译 → 录音/文件识别 → 译文复制/分享 → 额度和套餐查询。不保证从其他 App 自动读取聊天内容、抓取后台语音、自动发送消息或接管原生通话。若要自有 App 内直接承接商业消息，需另外评估官方商业消息 API、费用和账号迁移。

Windows 的数 GB Python/CUDA 模型包不能直接放进手机。手机可先做有明确计费的云端 ASR，后续再测量适配移动芯片的小模型；网络传输和存储策略需写入隐私说明。

账号共用 ≠ 数据已同步。CRM 跨端同步应采用租户/账号/平台命名空间、稳定客户 ID、增量游标、版本号、删除墓碑和冲突规则，保留已有每实例隔离，不能重建现有用户数据库。

## 5. 云端需要继续完善的基础

本次读取当前本地 `work/cloud-node/server.js`，确认已有 customer-login、customer-usage、customer-heartbeat、translate、speech-authorize、customer-subaccounts 路由；这不是浏览器扩展已实机接通的证明。当前公开 `/api/health` 已在前序发布验证为 MySQL 健康。

- 统一 API 适配器 + 版本化接口，旧桌面客户端不破坏。
- 服务端决定套餐、额度与权限；浏览器内容脚本只收到翻译结果和脱敏状态，不能得到后台 Bearer Token 或供应商 Key。
- 按设备管理可撤销会话；浏览器账号令牌先只放受保护的扩展会话存储，不收集客户的 WhatsApp Cookie。
- 原子额度账本增加客户端请求幂等键及租户绑定，避免断网/重试的重复扣费；服务商成功与客户最终余额需一致。
- 订阅、一次性加量包和续费采用不同权益项，定义到期、周期重置、降级、退款的语义。
- iOS/Android 订阅与网页销售要按上架地区和商店政策设计，不能默认任何 App 都能直接跳转外部收款；购买恢复、续费、退款以服务端验证通知为准。
- 独立区分 clientPlatform、clientVersion、设备在线状态、模型健康状态。浏览器未运行本地模型不能上报“本地模型正常”。
- CRM“今日新增”不等于广告归因。投放 ROI 需要额外采集经同意的渠道点击/活动参数、首次触点、订单关联和去重规则，不能只根据国家/电话号码推断 Facebook 或 Google 来源。

## 6. 官网结构与本地草稿

首屏价值主张 → 文字/语音/跟进能力 → 三步工作流程 → 多端状态 → 套餐方向 → 合作伙伴 → FAQ → 下载。

本地设计选择浅米白、森林绿与少量青柠绿，避免复制参考站深色界面。聊天内容为明确标注的合成示意，不引用真实客户号码或消息；无外部脚本、统计追踪、支付、表单、预约收集。

- Windows 下载应指向已验证的 `v0.7.38` GitHub 正式包，上线前再校验文件名与哈希。
- 浏览器扩展标注“上架准备中”，Android 标注“实机内测”；未获得公开分发结果前不提供虚假安装入口。
- 展示已确认的初步定价，同时明确“注册后人工开通”；在自动支付和自动发放实现前，不模拟订单成功。
- `noindex,nofollow` 保留，避免本地草案被误当正式商业承诺。
- 宣传页与云端后台分离；不得覆盖当前登录/管理入口或上传客户数据库。后续用独立域名或经确认的子域名部署静态资源。

### 上线前必须补齐

1. 经营主体、品牌与域名；不要把个人账户、API Key、数据库文件放入静态站。
2. 计费字符口径、一次性余额的长期管理、单账号单设备并发限制的技术落地、设备更换/撤销、公平使用与退款规则。
3. 正式客服联系方式与可验证的购买流程。
4. 隐私政策、服务条款、数据删除方式；披露第三方处理及模型许可证。
5. 真实脱敏演示、逐平台测试状态、下载哈希和变更日志。
6. 先以匿名页面浏览/下载转化验证获客，不采集聊天消息；需要统计时另行配置同意与最小化机制。

## 7. 执行顺序

**先浏览器云端接入 → 定价与官网上线 → Android/iPhone 独立 App MVP → 代理和更复杂的语音/企业产品。**

本轮交付官网本地预览与研究方案，不表示浏览器接入、手机研发、代理后台或支付已经完成。现有桌面和云端生产代码没有因制作官网而修改。
